# Maadori GUI（MFAAvalonia 定制版）实现评估

> 评估对象：本仓库 `MFAAvalonia/`（基线 v2.16.1，commit `4f11c81`，定制分支 `maadori-custom`）
> 对照对象：`C:\Users\Lee\Documents\Python\Maadori`（v1.6.8）
> 评估日期：2026-10-23

---

## 一、结论先说

**功能上够用，结构上有隐患，方向上不建议继续往里加东西。**

三条判断：

1. **MFA 只提供了"外壳"，Maadori 的 GUI 完成度主要由 `interface.json` 决定，而不是由 C# 定制决定。** 目前 `interface.json` 只用了 PI v2 的最小能力（12 任务 / 20 选项，0 个 `default_check`、0 个 `group`、0 个图标、0 个 `global_option`、0 个 `repeatable`）。用户感觉到的"界面简陋 / 配置要手改 yml"，八成是这里没做，不是 MFA 缺能力。
2. **MFA 侧 2603 行定制里，真正必要的不到一半。** 结构性问题集中在 `MaaProcessor.cs`（+863 行，占该文件 5887 行的 15%）：成绩图推送、画面缓存、日志渲染图这些**业务逻辑**被塞进了上游核心文件，且通过"目录文件轮询"与 agent 耦合。这是上游同步的最大冲突源。
3. **`mfa` 文件夹现在不要动。** 除一项"GUI 自更新指向上游仓库"的隐患（见 §5 P2，可用发布说明规避，不必改代码），其余缺口全部能在 `interface.json` + agent 侧消化。**只有当 GUI 需要新增页面级能力（战绩图表、日志查看器、配置编辑器）时才值得动 C#**，那属于另一个量级的投入。

## 四、结构合理性

### 4.1 `MaaProcessor.cs` 承担了不该承担的职责（主要问题）

`+863` 行里有 15 个新增私有方法/字段，横跨三个关注点：

- 通知附图：`_lastNotificationImage`、`StartNotificationImageCacheLoop`、`CaptureNotificationImage`、`WaitForControllerReconnect`
- 日志渲染：`CollectRecentLogEntries`、`RenderLogEntriesToPng`（含 `AdaptForeground` / `IsErrorLike` / 斑马纹 / 水印）
- 成绩图推送：`StartResultImageWatchLoop`、`ScanAndSendResultImagesAsync`、`PruneResultImageArchives`

三类东西都该在 `Helper/` 下的独立类里，`MaaProcessor` 只保留调用点（约 10 行）。现状的代价：

- 上游改 `MaaProcessor.cs` 时冲突面积达 863 行，实际 rebase 基本等于重做
- 渲染代码（Avalonia 控件树 + `RenderTargetBitmap`）与任务调度代码同文件，读代码要反直觉地跳转
- 没有单元测试的可能：想验证 `RenderLogEntriesToPng` 得启动整个 MFA

### 4.2 成绩图推送是"目录协议"，不是接口

链路：agent `NotifyResultImage` 写 `debug/notify_images/result_*.png` + 同名 `.json` → MFA 每 3s 扫目录 → 推送 → 移到 `sent/`。

- 路径一致性靠**约定**：agent 用 `cwd/debug/notify_images`（`paths.py:38-40` 注释明确写了"依赖 agent cwd == MFA 安装目录"），MFA 用 `AppContext.BaseDirectory + debug/notify_images`。任何一边 cwd 变了，功能静默失效。
- 已付出的代价：为了配对 `.png`/`.json`，MFA 侧写了"孤儿摘要归档"逻辑；为了归档不无限增长，两边各写一套 TTL 修剪（agent 24h/200 张，MFA 7 天）。**同一个清理语义在两端重复实现**。
- 多实例下曾导致同一张图重复推送（每实例一个循环），改静态单例才修掉 —— 说明这套协议天生缺乏"消费了一次"的确定性语义。

合理做法（若将来重构）：agent 通过 `AgentServer` 的自定义消息/回调把 `(png_bytes, caption)` 直接交给 MFA，或 MFA 侧按"文件锁 + 原子改名"消费。**但这不值得现在做** —— 现状能跑，重构收益是"以后好维护"。

### 4.3 静态单例读的是"当前实例"的设置

`ScanAndSendResultImagesAsync` 取 `Instances.ExternalNotificationSettingsUserControlModel`（当前激活实例）。循环是应用级常驻的，但开关判定跟当前实例走 —— 切换实例后行为随之变化，语义含糊。同类问题在 `StartResultImageWatchLoop` 的幂等启动上被掩盖了。

### 4.4 多实例与 Maadori 的业务模型冲突

MFA 多实例设计给"多台设备各跑一套"。Maadori 打歌是**独占一台模拟器**的重活，两个实例同时连同一设备会互抢 minitouch/IPC，结果不可预期。MFA 无跨实例互斥（`TaskQueueViewModel.StartTask` 只检查本实例 `IsRunning`）。

用户 `Maadori-runtime/appsettings.json` 里实际存在 2 个实例（`default` + `0c551aa0`）—— 这正是当初成绩图重复推送的现场。**建议在 Maadori 侧不做多开引导，README 明确"单实例使用"**。

### 4.5 `interface.json` 没吃到 PI v2 的红利

具体浪费（均为纯 JSON 改动，无需编译）：

- 无 `default_check` → 每次启动 12 个任务全不勾，"启动游戏 → 清火 → 退出"这套常用组合要手动勾三次
- 无 `group` → 任务列表无法按"启动类 / 演出类 / 收尾类"分层（注意：只在添加对话框生效，主列表仍扁平）
- 无 `icon` → 纯文字列表
- 无 `global_option` → "停止火力"复制了 4 份、"难度"复制了 6 份，改一处要改多处
- 无 `input` → 歌单/黑名单/偏移校准这类自由值彻底没有入口
- 无 `advanced` → 上游的"高级配置"折叠面板未启用

## 六、建议清单

### A. 不动 MFA 就能做（收益最高，成本最低）

1. **`interface.json` 补 `default_check`**：启动游戏 / 自由演出 / 退出游戏 默认勾选。
2. **`interface.json` 补 `icon` + `group`**：三类分组（启动 / 演出 / 收尾），配 12 个图标。
3. **用 `input` option 开配置入口**：优先做 3 个用户最常改的 ——
   - 歌单（多行文本，逗号/换行分隔）
   - 黑名单（同上）
   - `photogate_latency_ms` 时序补偿（int + `verify` 正则限 0-500）
   实现方式：`input` 的 `pipeline_override` 拼成 `custom_action_param` 的 JSON；agent 侧在 `load_config` 之后用参数覆盖。**这是零 C# 改动打通业务配置的唯一正路**，`actions.py` 里已有 5 处同款范式。
4. **`global_option` 收敛重复项**：难度、停止火力各收敛为一份全局项。
5. **README 补三件事**：配置文件的**确切路径**、定时任务怎么配、多开不要用。
6. **发布说明里声明"不要点更新软件"**，规避 P2-9。

### B. 轻量改 agent（不动 MFA）

7. **战绩查看**：agent 加一个"生成战绩报告"的自定义动作或托盘命令 → 读 `play_records.db` → 渲染 HTML → `webbrowser.open`。复用现有的成绩图渲染风格（1080px、斑马纹）。
8. **配置自检**：agent 启动时校验 `config.yml`，把"未知字段 / 非法值"以 `warn:` 前缀打到 MFA 日志面板（已有 `MFAFormatter` 机制），用户能自己发现写错。

### C. 需要动 MFA（仅在明确要"页面级能力"时）

9. **日志面板上限 150 → 2000**（一行常量）。若嫌改动上游文件，可在 `Maadori` 分部类里覆盖 —— 但 `MaxLogCount` 是 `private const`，只能改原处。
10. **设置页加"打开配置目录 / 打开日志目录"按钮**（`SettingsViewModel` 加两条命令，约 30 行）。
11. **战绩页面**：新页面 + 图表库，工作量最大（3-5 天量级）。**不建议** —— HTML 报告方案（B-7）能覆盖 90% 需求。
12. **重构 `MaaProcessor.cs` 的 863 行**：抽到 `Helper/Notification/MaadoriNotificationHelper.cs`，只为降低上游同步成本，无功能收益。**除非决定长期跟进上游，否则不做。**

## 七、`mfa` 文件夹要不要动？

### 结论：现在不动。

**理由（按权重）：**

1. **改动成本被分发机制放大。** 资源包更新（`interface.json` + `resource/` + `agent/`）能 OTA 到老用户；`MFAAvalonia.Core.dll` 变了一次就得让所有用户下 360MB 完整包覆盖安装。改一次 C# 的边际成本远高于改一次 JSON。
2. **当前缺口 8 成在 JSON 和 agent 侧。** P0/P1 共 8 项，只有 2 项（日志上限、目录按钮）必须动 C#，且都不是"没有就不成立"的功能。
3. **上游同步风险已经很高。** `MaaProcessor.cs` 863 行定制 + `ExternalNotificationHelper.cs` 383 行，rebase 到新版本基本等于手工重做。再往里加东西，等于把迁移成本继续推高。

### 什么情况下才动（触发条件）

| 触发条件 | 该做什么 |
|---|---|
| 要做战绩可视化**页面**（不只是 HTML 报告） | 新页面 + 图表库，独立于现有定制 |
| 日志面板成为**用户反馈的高频问题**（"看不到报错"） | 改 `MaxLogCount` + 加目录按钮，一次性小改 |
| 决定**长期跟进上游**（v2.17+ 有需要的特性） | 先做 §6-C12 的抽取重构，再 rebase，否则越拖越贵 |
| 成绩图推送**再次出现重复/漏发** | 重构为 AgentServer 回调，替换目录协议 |

### 一句话

**MFA 现在的定位应该是"冻结的运行时依赖"，不是"持续演进的产品界面"。** 要加功能就加到 `interface.json` 和 agent 里去；GUI 只在真被框架能力卡住时才碰。
