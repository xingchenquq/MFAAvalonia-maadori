# GUI 隔离改造 · 分步实施流程

> 依据：`docs/GUI实现评估-20261023.md`、`docs/GUI多产品隔离设计-20261023.md`
> 目标：把"三个产品共用一份构建产物"改造成"一份源码、按品牌出多份产物"，且全程不破坏 Maadori 的现有发版链。
> 日期：2026-10-23

---

## 一、第一步做什么

### 唯一的下一步：建立 Brand 化构建骨架（阶段 1）

**为什么是它，而不是先补 `interface.json`：**

1. **它是所有后续动作的物理前提。** 无论后面是补界面选项、加能力开关、还是给 MaaEOV 换图标，都得先回答"这次构建落到哪个目录"。通道没建好，改动就还是往公共目录里堆。
2. **它零破坏。** 不传 `-p:Brand=` 时行为完全不变（仍输出 `bin/AnyCPU/Release`），现有三条构建脚本一行不改也能跑。风险集中在"新增一条可选路径"，不动任何现有链路。
3. **它一次性解掉最大的静默失败源。** 编错目录不会报错，只会让用户在包里看到别家的图标和文案。这是唯一"错了也发现不了"的环节。
4. **它便宜。** 两个 csproj 各加一个 `PropertyGroup`，加一个 `Directory.Build.props` 属性块，半天含验证。

**不先做的事**：`interface.json` 的功能补齐（阶段 3）、能力开关 `#if`（阶段 2）。这两块在阶段 1 完成后再做，验证变量才可控。

---

## 二、总览

| 阶段 | 内容 | 改哪里 | 是否编译 | 破坏性 |
|---|---|---|---|---|
| **1** | Brand 化构建骨架 | 2 个 csproj + 1 个 props | 是 | 无（向后兼容） |
| **2** | 品牌资源与能力开关 | C# + 资源 + brand.props | 是 | 中（首次出现品牌差异） |
| **3** | interface.json 补功能 | 纯 JSON（Maadori 仓库） | 否 | 无（可随时回退） |
| **4** | 流程与运维规范 | skill / 文档 / 配置 | 否 | 无 |

阶段 2 与阶段 3 技术上可并行，但**建议串行**：阶段 2 会引入"同一份代码出不同产物"，阶段 3 的验证需要稳定的产物对照基准。

### Step 1.1 · `Directory.Build.props` 加 Brand 解析

**目标**：让 `-p:Brand=Maadori` 成为一个全局可识别的构建维度，非法值直接报错（而不是静默产出到默认目录）。

**前置**：Step 1.0 完成。

**操作**：在 `Directory.Build.props` 的 `<Project>` 内、现有 `<ItemGroup>` **之前**插入：

```xml
  <PropertyGroup>
    <Brand Condition="'$(Brand)' == ''"></Brand>
    <_BrandAllowed>Maadori;Maaon;MaaEOV</_BrandAllowed>
    <_BrandValid Condition="'$(Brand)' == ''">true</_BrandValid>
    <_BrandValid Condition="'$(Brand)' != '' and $([System.String]::Copy(';$(_BrandAllowed);').Contains(';$(Brand);'))">true</_BrandValid>
    <BrandRoot Condition="'$(Brand)' != ''">$(MSBuildThisFileDirectory)brands/$(Brand)</BrandRoot>
  </PropertyGroup>

  <Error Condition="'$(Brand)' != '' and '$(_BrandValid)' != 'true'"
         Text="未知 Brand '$(Brand)'。可选：$(_BrandAllowed)" />

  <PropertyGroup Condition="'$(Brand)' != ''">
    <DefineConstants>$(DefineConstants);BRAND_$([System.String]::Copy('$(Brand)').ToUpperInvariant())</DefineConstants>
    <ProductBrand>$(Brand)</ProductBrand>
  </PropertyGroup>
```

要点：
- `Brand` 为空是合法状态（= 纯上游基线构建），保持向后兼容
- `DefineConstants` 注入 `BRAND_MAADORI` / `BRAND_MAAON` / `BRAND_MAAEOV`，供阶段 2 的 `#if` 使用
- `BrandRoot` 指向 `brands/<Brand>/`，阶段 2 用它取图标与覆盖资源

**产出**：`Directory.Build.props` 新增约 15 行。

**验证**：
```bash
dotnet build MFAAvalonia.Desktop/MFAAvalonia.Desktop.csproj -c Release -p:Brand=Bogus
# 期望：报错 "未知 Brand 'Bogus'"，且不产出
dotnet build MFAAvalonia.Desktop/MFAAvalonia.Desktop.csproj -c Release
# 期望：正常通过，产物仍在 bin/AnyCPU/Release
```

**回退**：删除新增的 `<PropertyGroup>` 与 `<Error>`。

### Step 1.2 · 拆输出目录（Desktop 工程）

**目标**：`-p:Brand=X` 时产物落到 `bin/X/Release/`，与 `bin/AnyCPU/Release` 物理分离。

**前置**：Step 1.1 通过。

**操作**：在 `MFAAvalonia.Desktop/MFAAvalonia.Desktop.csproj` 里，**在现有那个含 `<OutputPath>../bin/$(Platform)/$(Configuration)/</OutputPath>` 的 `PropertyGroup` 之后**，追加：

```xml
    <PropertyGroup Condition="'$(Brand)' != ''">
        <OutputPath>../bin/$(Brand)/$(Configuration)/</OutputPath>
        <IntermediateOutputPath>obj/$(Brand)/$(Configuration)/$(TargetFramework)/</IntermediateOutputPath>
    </PropertyGroup>
```

要点：MSBuild 后定义的属性覆盖先定义的，所以无需改原行 —— **原路径保持原样是刻意的**，"不传 Brand 就一切照旧"这个承诺靠它兑现。

**产出**：`bin/Maadori/Release/`（首次构建后约 350+ 文件、含 `libs/`、`runtimes/`、`plugins/`、各语言目录）。

**验证**：
```bash
dotnet build MFAAvalonia.Desktop/MFAAvalonia.Desktop.csproj -c Release                    # → bin/AnyCPU/Release
dotnet build MFAAvalonia.Desktop/MFAAvalonia.Desktop.csproj -c Release -p:Brand=Maadori   # → bin/Maadori/Release
```
两个目录的 `MFAAvalonia.Core.dll` 关键字符串命中数应**完全一致**（因为此刻代码没变）。

**回退**：删掉这个 `PropertyGroup`，`rm -rf bin/Maadori obj/Maadori`。

### Step 1.3 · 拆中间产物（类库工程）

**目标**：`MFAAvalonia.Core` 的 `obj/` 也按 Brand 分开，为阶段 2 的 `#if` 能力开关铺路（否则增量构建会复用另一个品牌编出的 dll）。

**前置**：Step 1.2 通过。

**操作**：在 `MFAAvalonia/MFAAvalonia.csproj` 的 `<PropertyGroup>`（含 `AssemblyName` 那个）之后追加：

```xml
    <PropertyGroup Condition="'$(Brand)' != ''">
        <IntermediateOutputPath>obj/$(Brand)/$(Configuration)/$(TargetFramework)/</IntermediateOutputPath>
    </PropertyGroup>
```

**不动** `BaseIntermediateOutputPath` —— 它必须在 `Microsoft.Common.props` 之前生效，挪到 `Directory.Build.props` 里会连带改变 `project.assets.json` 的位置，容易出现 restore 类疑难问题。代价是 `LazyStaticGenerated` 目录仍共享；若阶段 2 出现"改了 `#if` 却编出旧产物"，用 `dotnet build --no-incremental` 解决，或届时再处理。

**产出**：`MFAAvalonia/obj/Maadori/Release/net10.0/`。

**验证**：连续两次构建不同 Brand，两次的 `MFAAvalonia/obj/<Brand>/` 各自独立，互不覆盖。

**回退**：删掉该 `PropertyGroup`。

## 八、明确不做的事

- **不做程序集级隔离**：源码里 26 处 `avares://MFAAvalonia.Core/...` 硬依赖 `AssemblyName`，改名必然白屏。隔离只能靠 exe 改名 + 目录。
- **不 fork 三个仓库**：定制只有 2603 行且高度同质，fork 三次等于上游同步 ×3。
- **不动 `BaseIntermediateOutputPath`**：改它会连带搬移 `project.assets.json`，容易出 restore 疑难，收益不值。
- **不在阶段 1 里顺手改业务逻辑**：阶段 1 的唯一目的是"让产物能分家"，混入功能改动会让验证失去对照基准。
