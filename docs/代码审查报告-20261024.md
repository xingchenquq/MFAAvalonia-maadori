## 0. 一句话结论

## 2. 结构问题

### 2.1 MaaProcessor 是典型的上帝类（P1，最严重）

`Extensions/MaaFW/MaaProcessor.cs`，5,892 行、272 个成员、一个文件、**没有 partial**。

看它的 `using` 就能看出职责已经失控：

```csharp
using Avalonia.Controls;              // UI 控件
using Avalonia.Controls.Notifications;
using Avalonia.Media.Imaging;         // 位图
using Microsoft.WindowsAPICodePack.Taskbar;  // Windows 任务栏
using MFAAvalonia.Views.Windows;      // 直接依赖 View
using SukiUI.Dialogs;
using MaaFramework.Binding;           // 核心业务
```

一个"处理器"同时干这些事：

1. pipeline / resource 加载与解析
2. 任务队列调度与状态机（`TaskQueueResult`、`_taskQueueTotal`）
3. controller 连接、ADB 重试、设备选择
4. 截图 / live view / 截图专用 tasker 生命周期
5. 日志收集、裁剪（`LogItemViewModels`、`TrimExcessLogs`）
6. 平台进度上报（`PlatformRunProgress`、`RunLogEntry`）
7. 通知截图缓存循环（自研 `StartNotificationImageCacheLoop`）
8. 节点参数（内嵌 `NodeAndParam` 类）
9. Windows 任务栏进度

**自研增量的问题在这里体现得最明显**：本次分支往这个类里塞了 868 行，其中两大块（+301 行、+428 行）是 QQ 通知截图相关逻辑。代码本身写得不差——注释甚至记录了实测证据（`Tasker.Task.Succeeded` 与 `Controller.Action.{inactive}` 相差 1ms）——但它**本该是独立的 `NotificationImageService`**，而不是让 5,892 行变成 6,760 行。

**建议**：零行为变更的最小拆法是先加 `partial`，按职责切成 6 个文件：

```
MaaProcessor.cs                 核心字段 + 生命周期（~600 行）
MaaProcessor.TaskQueue.cs       任务队列与状态机
MaaProcessor.Controller.cs      连接、设备、ADB 恢复
MaaProcessor.Screenshot.cs      截图 / live view / 截图 tasker
MaaProcessor.Logging.cs         日志与平台进度
MaaProcessor.Notification.cs    QQ 通知取图（自研部分，最终抽成独立服务）
```

`partial` 只是止痛药，但成本接近零、风险接近零，可以先走这一步。真正的目标是把 2/4/5/7 抽成独立协作者类，由 `MaaProcessor` 持有引用。

### 2.2 分层被反向依赖破坏（P1）

`Helper/` 本该是无 UI 依赖的基础设施层，实际有 **33 处 `using MFAAvalonia.ViewModels/Views`**：

```
Helper/Instances.cs            → Views.Pages, Views.UserControls.Settings, Views.Windows
Helper/TaskOptionGenerator.cs  → ViewModels.Pages, Views.UserControls
Helper/TrayIconManager.cs      → ViewModels.Windows, Views.Windows
Helper/ToastNotification.cs    → Views.Windows
Helper/TelemetryService.cs     → ViewModels.Windows
Helper/DirectoryMerger.cs      → ViewModels.Windows   ← 目录合并跟 ViewModel 有什么关系？
```

再加上 `MaaProcessor`（Extensions 层）引用 `Views.Windows`，实际的依赖图里 `Helper → ViewModels → Extensions → Helper` 是一个**环**。

后果很实在：`TaskOptionGenerator` 明明在 Helper 里，却需要 `TaskQueueViewModel` 才能工作；而 `TaskQueueView.axaml.cs` 又在 View 里 `new TaskOptionGenerator(vm, SaveConfiguration)`。逻辑归属完全说不清。

`DirectoryMerger` 引用 `ViewModels.Windows` 是典型的"为了拿 `Instances.RootViewModel` 报个进度"——进度回调本该通过构造参数或接口传入。

### 2.3 静态服务定位器（P2，但限制了长期演进）

`Helper/Instances.cs` 是 `static partial class`，配 `LazyStaticGenerator` 生成静态属性，内部 `Resolve<T>()` 走 `App.Services.GetRequiredService<T>()` + `ConcurrentDictionary<Type, Lazy<object>>` 缓存。

这套机制本身设计得挺细（有设计时模式兜底、有循环依赖提示、有精确的错误信息，比裸单例好），但代价是：

- `Instances.Foo` 出现在代码里，**依赖关系在编译期完全不可见**。改一个 ViewModel 的构造函数，没人知道会炸哪。
- `Helper` 内就有 **144 处 `Instances.`**。
- 单例 = 全局可变状态。而 Maadori 支持多实例，靠 `InstanceId` 手工路由：

```csharp
// ConfigurationManager.cs:34
public static InstanceConfiguration CurrentInstance =>
    MaaProcessorManager.Instance?.Current?.InstanceConfiguration ?? new InstanceConfiguration("default");
```

最后那个 `?? new InstanceConfiguration("default")` 是隐患——初始化顺序错的时候不报错，直接静默操作一个幽灵实例。

**建议**：不追求全面 DI 化（代价太大），只做两件事：
1. 新代码禁止用 `Instances.`，改成构造函数注入；`Instances.` 只作为历史遗留的兼容出口。
2. 把 `ConfigurationManager.CurrentInstance` 的兜底 `new` 改成抛异常。**让错误尽早暴露，比让它静默跑错强。**

### 2.4 UI 逻辑堆在 code-behind（P2）

`TaskQueueView.axaml.cs` 2,951 行，其中 `SetOption` 一个方法 139 行，直接在 View 里 `new StackPanel()`、维护 `CommonPanelCache`、手动切 visibility：

```csharp
var newPanel = CommonPanelCache.GetOrAdd(cacheKey, key =>
{
    var p = new StackPanel();
    new TaskOptionGenerator(vm, SaveConfiguration).GenerateResourceOptionPanelContent(p, dragItem);
    CommonOptionSettings.Children.Add(p);
    return p;
});
newPanel.IsVisible = true;
```

这是典型的"用代码造 UI"而不是"用模板描述 UI"。正确做法是给选项面板定义 `DataTemplate`，让 `ItemsControl` 自己管生成和复用，View 只负责绑定。缓存都省了。

同样的问题在 `DashboardCardGrid.cs`（2,950 行，还自己开 `DispatcherPriority.Render` 的定时器）。

## 3. 性能问题

### 3.1 UI 线程上的同步阻塞（P1，有死锁风险）

`.Wait()` / `.Result` 共 40 处，最集中的是 `Extensions/MaaFW/MaaExtensions.cs`——12 个扩展方法全是同步版本：

```csharp
public static void Click(this MaaTasker maaTasker, int x, int y) => maaTasker.Controller.Click(x, y).Wait();
public static void Swipe(...) => maaTasker.Controller.Swipe(...).Wait();
public static void Screencap(...) => maaTasker.Controller.Screencap().Wait();
```

还有 `MaaInterface.cs` 中 5 处：

```csharp
DisplayDescription = LanguageHelper.GetLocalizedString(Description.ResolveContentAsync().Result);
```

在属性 getter/setter 里同步等待异步方法 —— 只要有 `SynchronizationContext`（Avalonia UI 线程就有），且 `ResolveContentAsync` 内部有 `await` 无 `ConfigureAwait(false)`，就是标准死锁配方。

`FocusHandler.cs:261` 的注释更是直接承认了：

```csharp
// 阻塞式弹窗：InvokeAsync 返回 Task，.Wait() 阻塞回调线程直到用户关闭弹窗
...
})).Wait();
```

在 native 回调线程上 `Wait()` 一个需要 UI 线程执行的委托，**UI 线程一旦忙（比如在等这个回调），直接死锁**。这类 bug 现场表现为"偶发卡死"，是最难查的一类。

**建议**：给 `MaaExtensions` 补 async 版本，逐步替换调用点；`FocusHandler` 改成 `TaskCompletionSource` + 回调，不要在回调线程上等。

### 3.2 轮询式 Sleep（P1）

`Thread.Sleep` 182 处。没有统一的退避策略，各处自己写 `Sleep(500)` / `Sleep(1000)` / `Sleep(3000)`。

问题不在"用了 Sleep"（native 交互确实需要等），而在于：
- 固定间隔，不响应取消 token
- 无法统一调优，也没有单点开关
- 任务停止时无法快速退出

**建议**：统一成 `await Task.Delay(ms, ct)`，至少做到可取消。这是低风险、高收益的机械改造。

### 3.3 定时器分散、各自刷新（P2）

`DispatcherTimer` 至少 10 处，分散在 View 和 VM 层：

```
ViewModels/Pages/MonitorViewModel.cs
ViewModels/Pages/TaskQueueViewModel.cs        运行时长
ViewModels/Other/TimerModel.cs
Views/Mobile/MobileTaskQueueView.axaml.cs      预览统计
Views/UserControls/Dashboard/DashboardCardGrid.cs   用 DispatcherPriority.Render
Views/UserControls/MarqueeTextBlock.axaml.cs   跑马灯
Views/UserControls/TeachingTipOverlay.axaml.cs
Views/Windows/NotificationView.cs
```

没有统一帧调度，意味着同一时刻可能有 4~5 个回调挤在 UI 线程上抢时间片。跑马灯和 Dashboard 卡片这类纯视觉效果，更应该合并到一个统一的渲染节拍里，或者在不可见时彻底停掉。

### 3.4 日志高频路径

`MaaProcessor` 里每条 `AddLog` 会触发：`ObservableCollection` 变更通知 → `PublishPlatformLog` → 每通道 ARGB 位运算转换 → 150 条上限检查 + 批量裁剪。

任务运行时日志是高频写入的。`MaxLogCount = 150` + `LogCleanupBatchSize = 30` 已经做了批量化，思路是对的，但每条日志仍然逐个走一遍集合通知。可以改成批量 `AddRange` + 单次 `Reset` 通知。

### 3.5 零散点

- `public static readonly Random Random = new()` — `Random` 实例在多线程下共享不安全。项目是 net10.0，直接用 `Random.Shared`。
- `public bool IsV3 = false;` — 公开可变字段，应该是只读属性。
- `Bitmap` / `Brushes` 在 `MaaProcessor` 里出现，意味着图像对象生命周期跟业务对象绑在一起，释放时机不可控（截图层本来最容易漏 Dispose）。

### 5.1 测试覆盖 ≈ 0（P0，这是最大的风险）

全项目唯一测试项目：`Markdown.Avalonia.Html.Tests`（1,521 行，xUnit）。

问题是——**它测的是 vendored 的第三方 Markdown 库，不是自研代码。**

**建议（这是唯一值得排 P0 的事）**：

不要想着补覆盖率，先建**第一个测试项目**，只测"纯逻辑、无 UI 无 native"的部分。这些是现成的可测点：

```
  Extensions/MaaFW/TaskQueueStateTests.cs      任务状态机迁移
```

十个测试就够。目标不是覆盖率，是**在 CI 里立起 `dotnet test` 这道闸**。有了闸，后面才谈得上加测试。

### 5.2 没有 lint gate（P0，成本最低）

仓库里**没有 `.editorconfig`**，也没有任何 analyzer 规则包（Roslynator / StyleCop / SonarAnalyzer）。`MFAAvalonia.csproj` 里没有 `TreatWarningsAsErrors`。

`MaaProcessor.cs` 顶部甚至直接关掉了三个警告：

```csharp
#pragma warning  disable CS4014 // 由于此调用不会等待...
#pragma warning  disable CS1998 // 此异步方法缺少 "await" 运算符...
#pragma warning disable CA1416 //  可在 'linux', 'macOS/OSX', 'windows' 上访问此调用
```

CS4014（未 await 的 Task）被全局关掉，是最值得警惕的一条——fire-and-forget 的任务异常会静默丢失。前面那 15 个 `async void` 也是同类问题。

**建议**：加 `.editorconfig` + 少量 analyzer，先设 `Severity = warning` 跑一遍拿到存量清单，再挑低风险类别升到 `error`。不要一次性全开，会淹没。

### 5.5 品牌化机制（做得对，应作为模板）

`-p:Brand` 这套东西质量明显高于周围代码，值得单独点出来：

- `Directory.Build.props` 里 `ValidateBrand` target 在 `PrepareForBuild` 前硬失败，非法品牌不会静默产出
- `Directory.Build.targets` 里 `DefineConstants` 注入时机正确（注释里解释了为什么必须在 targets 而不是 props）
- `MFAAvalonia.csproj` 里 `OutputPath` 也做了品牌化，注释记录了"文件大小完全相同、肉眼看不出来"的踩坑
- `BrandCapabilities` 用运行时读元数据而非 `#if`，理由写清楚了

这就是"注释解释为什么"的正确示范。**新代码向这个标准看齐。**

## 7. 一句话总结

**结构上，最大的病是 `MaaProcessor` 这个 5,892 行的上帝类——而自研增量正在往上面继续加行。性能上，真正的风险不是慢，是 UI 线程上的 40 处同步等待带来的偶发死锁。可维护性上，6.6 万行自研代码零测试、CI 不跑测试、没有 lint 规则，这是比任何代码坏味道都严重的结构性缺陷。**

好消息是：注释习惯、品牌化机制、构建约定这些"工程文化"层面做得好，说明作者知道什么是好的。现在缺的不是意识，是**自动化护栏**——把"知道该怎么做"变成"做不到就过不了 CI"。

先花一周建护栏，再谈重构。
