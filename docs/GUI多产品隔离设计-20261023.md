# 多产品共用 GUI 外壳：隔离设计评估

> 评估日期：2026-10-23
> 涉及产品：Maadori（邦多利国服打歌）、Maaon（交织的乐章打歌）、MaaEOV（异象回声）
> 共享对象：`C:\Users\Lee\Documents\Python\MFAAvalonia`（MFAAvalonia v2.16.1 定制 fork）

---

## 一、结论

**需要隔离，但粒度为"构建期 + 目录级"，不是 fork 级。**

三句话：

1. **当前不是"统一 GUI"，而是"一份源码被三个产品隐式共享"。** 三个产品的 `build_mfa.py` / `build_gui_mfa.sh` 都从同一个源码目录、同一个 `bin/AnyCPU/Release` 取壳。这不是设计，是巧合堆出来的状态 —— 谁改了 C#、进了哪个包，全靠人记。
2. **最危险的两个单点：共享的 `bin/AnyCPU/Release`（定制无偿渗透）和共享的框架版本（升级互相绑架）。** 这两个必须优先拆。
3. **不要 fork 三次。** 把品牌差异抽成编译参数（`-p:Brand=`），一份源码出三个产物。改造约 1-2 天，之后每个产品加功能只是改一个 `brands/<Brand>/` 目录。

### 2026-10-23 决策修订（已落地，部分覆盖上面的第 3 条）

实际采用的是**两层隔离**，比"一份源码出三品牌"更彻底：

| 产品 | MFA 来源 | 版本策略 |
|---|---|---|
| **Maadori** | 本仓库独占（`maadori-custom`） | 跟随定制分支 |
| **MaaEOV** | 项目内副本 `MaaEOV/vendor/MFAAvalonia`（自带 `.git`） | 固定上游 tag，由 `scripts/sync_mfa_src.sh` 切换 |
| **Maaon** | 待定，若启用同样走 vendor 副本 | — |

**为什么放弃"一份源码出三品牌"**：`-p:Brand` 能隔离"功能是否生效"（QQ 卡片显不显示），
但隔离不了**代码本身** —— MaaEOV 仍要跟 Maadori 的 2603 行定制一起编译、一起承担 bug 面，
而且一次 `git checkout` 就能把两边的分支状态搅在一起。品牌参数只是"开关"，独立副本才是"隔离"。

`-p:Brand` 机制保留并在 Maadori 上使用（保证 `ProductBrand` 元数据正确、发版校验能识别），
但对 MaaEOV 已非必需 —— 它的副本里根本没有定制代码可关。

详见 `MaaEOV/docs/MFA源码隔离-20261023.md`。

**不需要隔离的部分同样重要**：上游框架代码、通用 UI、主题基座必须共享，否则上游同步成本 ×3，项目会被维护成本压死。

## 二、现状：共享面与隔离面

### 2.1 共享的东西（隐患所在）

| 共享对象 | 事实 | 风险 |
|---|---|---|
| **源码目录** | Maadori `build_mfa.py`、Maaon `build_mfa.py`、MaaEOV `scripts/build_gui_mfa.sh` 全部指向同一个 `MFAAvalonia` | 改一处影响三产品，无回归矩阵 |
| **构建产物** | 三者都从 `bin/AnyCPU/Release` 取 `MFAAvalonia.exe` + `MFAAvalonia.Core.dll` | **一次编译，定制无偿进入所有包** |
| **框架版本** | `MFAAvalonia.csproj:63-64` 唯一锁 `Maa.Framework 5.10.0` / `Runtimes 5.12.3` | MaaEOV 升 GUI 必然升框架 → Maadori/Maaon 的 pipeline 要跟着迁 v5 语法 |
| **品牌资源** | `Assets/logo.ico` 已被替换为 Maadori 图标；resx 内硬编码「Maadori通知」 | Maaon/MaaEOV 包内会出现 Maadori 图标与文案 |
| **定制能力** | QQ 通知、成绩图推送、日志转图无开关，编进 Core.dll 就跑不掉 | MaaEOV 用户会看到一个用不上的 QQ 机器人设置页 |
| **git 工作区** | MaaEOV 升级流程 `git checkout <tag>`（`maaeov-gui-upgrade` skill Step 2）直接操作共享目录 | 切走分支 → Maadori 定制分支状态被破坏 |

**已验证的反例**：`MaaEOV.exe`（2026-09-13 编译，94.6MB）中 `ExternalNotificationQQBotAppId` / `QQBotLogAsImage` 均为 0 次命中 —— 那次编译早于定制落地，侥幸干净。**但机制没变，下次构建就会带上。**

### 2.2 已经天然隔离的东西（不用再操心）

| 对象 | 机制 | 证据 |
|---|---|---|
| 安装目录与配置 | `AppPaths.InstallRoot => AppContext.BaseDirectory`，config/logs/temp/instances 全在包内 | `Helper/AppPaths.cs:13-31` |
| 单实例互斥 | Mutex key = `SHA256(exe 绝对路径 + exe hash + Core.dll hash)` | `AppRuntime.cs:137-149` |
| 进程身份 | exe 改名（Maadori.exe / Maaon.exe / MaaEOV.exe） | 各 build 脚本 |
| 资源与更新包 | 各自的 packaging 脚本、各自的 `interface.url` | — |
| agent 配置 | Maadori 用 `%APPDATA%\Maadori\config.yml` | `src/maadori/config.py:497-507` |

**结论：进程级隔离已经成立，不需要额外做什么。真正缺的是"同一份源码怎么出三个不串味的产物"。**

## 三、需要隔离的维度（8 项，分三档）

### 档位 A —— 必须硬隔离（不隔离必出事）

| # | 维度 | 现状 | 建议粒度 | 手段 |
|---|---|---|---|---|
| A1 | **构建产物** | 共用 `bin/AnyCPU/Release` | 产品级目录 | `-p:BaseOutputPath=bin/<Brand>/`，输出 `bin/Maadori/Release/`、`bin/Maaon/Release/`、`bin/MaaEOV/Release/` |
| A2 | **框架版本** | 单一 `csproj` 锁死 5.12.3 | 产品级版本锁 | `Directory.Build.props` 里按 Brand 条件选择 `Maa.Framework.Runtimes` 版本；配套 `requirements.txt` 的 `MaaFw==X` 同步锁 |
| A3 | **品牌资源** | `logo.ico` 被直接替换进源码 | 产品级资源目录 | `brands/<Brand>/logo.ico` + `-p:ApplicationIcon=`；resx 品牌字样改为运行时读 `interface.json` 的 `label` |
| A4 | **能力开关** | 定制代码无条件编入 | 编译期开关 | `-p:EnableQQBotNotify=true` / `-p:EnableResultImagePush=true`，用 `#if` 或 MSBuild `DefineConstants` 包住 |
| A5 | **发布通道 / 更新源** | GUI 自更新硬编码 `MaaXYZ/MFAAvalonia`（`VersionChecker.cs:2530-2532`） | 产品级，且**必须关闭** | 编译期常量或直接禁用「更新软件」按钮；资源更新走各自 `interface.url` |

### 档位 B —— 建议隔离（现状可用，但语义模糊）

| # | 维度 | 现状 | 建议 |
|---|---|---|---|
| B1 | **运行时状态** | 按安装目录隔离（已 OK） | 保持。新增任何全局状态时坚持挂在 `InstallRoot` 下，禁止写 `%LOCALAPPDATA%` 之类的固定路径 |
| B2 | **agent 配置** | Maadori 用 `%APPDATA%\Maadori`，Maaon 未定，MaaEOV 用包内 `config/` | 统一约定：`%APPDATA%\<Brand>\config.yml`，Brand 与 `interface.json` 的 `name` 一致 |
| B3 | **日志与诊断** | 包内 `logs/`，天然隔离 | 保持；保证三个产品的日志格式一致，便于复用排查经验 |

### 档位 C —— 明确不要隔离

| # | 维度 | 理由 |
|---|---|---|
| C1 | 上游框架代码（`MFAAvalonia/` 主工程） | 一旦 fork 三次，上游同步成本 ×3，这是最不该付的税 |
| C2 | 通用 UI：任务队列、设置页、通知框架、实时画面 | 三产品需求高度重合，共享才有规模效应 |
| C3 | 主题基座（SukiUI、Markdown.Avalonia 全家桶） | 纯依赖，改不改都不影响产品差异 |
| C4 | NuGet 依赖版本（除 A2 的框架版本） | 版本分裂会带来编译期噪声，收益为零 |

## 四、五种隔离方案与取舍

### 方案 1：维持现状（隐式共享）

- **做法**：一份源码、一份产物，靠"编译时人工确保分支干净"。
- **适用**：只有 1 个产品时。
- **优点**：零成本。
- **缺点**：品牌渗透、版本绑架、回归矩阵不可控、git 状态污染。**三个产品时不可接受。**

### 方案 2：完全运行时品牌化（单 exe 服务所有产品）

- **做法**：只出一个 `MFAAvalonia.exe`，启动时读 `interface.json` 的 `name` 决定图标、文案、能力开关。
- **适用**：产品差异纯属"文案 + 开关"，且框架版本完全一致。
- **优点**：真正一次构建；用户分发仍是各包独立，但内部零差异维护。
- **缺点**：**图标是编译期资源（`-p:ApplicationIcon`），运行时换不了**；框架版本必须完全一致（MaaEOV 要升 → 全体跟）；能力差异要靠运行时配置，容易被用户误开。
- **判断**：不可行，卡在图标与框架版本两处硬约束。

### 方案 3：单源码 + 构建期品牌化（**推荐**）

- **做法**：
  ```
  MFAAvalonia/                     # 一份源码，品牌无关
  ├─ brands/
  │   ├─ Maadori/  brand.props  logo.ico  Strings.override.resx
  │   ├─ Maaon/    brand.props  logo.ico
  │   └─ MaaEOV/   brand.props  logo.ico
  ├─ Directory.Build.props        # 按 -p:Brand 引入对应 brand.props
  └─ bin/<Brand>/Release/         # 每个产品独立输出
  ```
  构建命令：`dotnet build ... -p:Brand=Maadori` → `bin/Maadori/Release/`。
- **适用**：产品差异 = 品牌资源 + 能力开关 + **框架版本可能不同**。
- **优点**：
  - 上游同步只做一次
  - 定制边界由编译参数强制，不靠人记
  - 能容忍 MaaEOV 与 Maadori 用不同 MaaFramework 版本（关键）
  - 每个产品的构建可复现（源码状态 + Brand 参数 = 确定的产物）
- **缺点**：首次改造（抽 brand.props、参数化资源、加 `#if` 开关）约 1-2 天；`csproj` 里会出现条件逻辑，需要写清楚。
- **这是三产品场景下的正解。**

### 方案 4：仓库级 fork（每产品一份源码）

- **做法**：Maadori 一个 repo、Maaon 一个 repo、MaaEOV 一个 repo。
- **适用**：产品间的 C# 改动量差异极大（比如一个要改任务队列布局，一个要加图表页）。
- **优点**：隔离最彻底，互不影响。
- **缺点**：上游 rebase 要做三次；bug 修三次；定制逻辑（如 QQ 通知 383 行）复制三份会漂移。**当前定制只有 2603 行且高度同质，fork 三次纯亏。**

### 方案 5：零 fork（官方二进制 + interface.json/agent 定制）

- **做法**：不编译任何 C#，直接用官方 MFAAvalonia Release，品牌靠 exe 改名 + interface.json。
- **适用**：不需要任何 GUI 层定制。
- **优点**：零维护，上游随更随用。
- **缺点**：QQ 通知渠道、成绩图推送、日志转图全部做不到（都改在 C# 层）。
- **判断**：Maaon 如果暂时不需要 QQ 通知，**可以走这条**；Maadori 不行。

### 方案对比

| 维度 | 1 现状 | 2 运行时品牌 | 3 构建期品牌 | 4 仓库 fork | 5 零 fork |
|---|---|---|---|---|---|
| 上游同步成本 | 1× | 1× | **1×** | 3× | 0 |
| 品牌渗透风险 | 高 | 中 | **低** | 无 | 无 |
| 框架版本独立 | ❌ | ❌ | **✅** | ✅ | ✅ |
| 能力开关 | ❌ | 运行时 | **编译期** | ✅ | 不适用 |
| 首次改造 | 0 | 中 | **1-2 天** | 3 天+ | 0 |
| 适合产品数 | 1 | 2（版本必须一致） | **2-5** | 5+ 且差异大 | 任意 |

## 五、推荐默认做法

### 5.1 选型

**方案 3 为主，方案 5 为边界。**

- 主干：一份源码 + `brands/` 目录 + `-p:Brand=` 参数化构建。
- 边界规则：**能用 interface.json / agent 解决的需求，一律不要动 C#**。这条已经在上一份评估里成立 —— Maadori 的 8 项 P0/P1 缺失有 6 项不用改 C#。新品（Maaon）如果没有 GUI 层刚需，默认走方案 5（官方二进制），等真有需求再纳入方案 3。

### 5.2 落地步骤（按依赖顺序）

1. **拆构建产物目录**（半天，收益最大）
   `Directory.Build.props` 加 `BaseOutputPath`，按 `$(Brand)` 分目录。三个 build 脚本的 `--mfa-dir` 改成各自目录。
   **必须做的原因**：现在三个产品共用一个 `bin/Release`，是"改一处污染三处"的物理通道。

2. **品牌资源外置**（半天）
   `Assets/logo.ico` 从源码树挪到 `brands/<Brand>/logo.ico`；`brands/<Brand>/brand.props` 里定义 `ApplicationIcon` / `AssemblyTitle` / `Product` / `Company`。
   MaaEOV 目前已经是这个模式（`build_gui_mfa.sh` 用 `-p:ApplicationIcon=$MFA_ICON` 注入），**直接沿用它，把 Maadori 的"替换文件"改造成同一套**。

3. **能力开关参数化**（半天）
   QQ 通知 / 成绩图推送 / 日志转图 三块加 `DefineConstants`
   （`-p:EnableQQBotNotify=true`）。只在 Maadori 的 `brand.props` 里打开。
   好处：MaaEOV 的包里不再出现用不上的 QQ 机器人设置页。

4. **品牌字样去掉硬编码**（1 小时）
   `LangKeys.ExternalNotificationSourceLabel` 的值"Maadori通知"改为运行时取
   `MaaProcessor.Interface?.Label ?? "MFA"`。`interface.json` 本来就有 `label` 字段
   （Maadori：`"Maadori 邦多利小助手"`；**MaaEOV 的 label 是 `null`，需补**）。

5. **框架版本按 Brand 锁**（1 小时 + 各产品验证）
   `Directory.Build.props` 里按 `$(Brand)` 条件覆盖 `Maa.Framework.Runtimes` 版本；
   对应 `requirements.txt` 的 `MaaFw==` 同步改。**这条解掉"升一个等于升全部"的绑架。**

6. **升级流程加约束**（流程，非代码）
   MaaEOV 的 `git checkout <tag>` 改为 `git worktree add` 或独立 clone。
   **不要在一个被三个产品共享的工作区里切分支。** 这是当前最容易踩的雷。

### 5.3 理由

- **为什么不是 fork**：定制只有 2603 行且三产品同质，fork 的边际收益（隔离）远小于边际成本（同步 ×3）。
- **为什么必须拆产物目录**：这是唯一"一次疏忽就静默出错"的地方 —— 编错目录不会报错，只会让用户在包里看到别人的品牌。
- **为什么框架版本要能独立**：这是硬约束链 `GUI 框架版本 ↔ agent maafw 版本 ↔ pipeline 语法`（`docs/MFA集成.md:68-82` 已写明）。共享一个版本 = 一个产品升级逼三个产品改 pipeline。MaaEOV 的升级 skill 里"pipeline v5 迁移"就是这条链的代价。
- **为什么进程/配置层不用管**：`AppPaths` 用 `InstallRoot`、单实例 key 含 exe 路径与 hash —— 天然隔离已经成立，再包一层只是增加复杂度。

## 六、如果不做隔离，潜在风险清单

| 风险 | 触发条件 | 后果 | 概率 |
|---|---|---|---|
| 品牌渗透 | 任一产品重建包 | 用户看到别家图标/文案，被质疑"套壳" | **高**（机械必然） |
| 版本绑架 | MaaEOV 升 GUI | Maadori/Maaon 的 pipeline 被迫迁 v5，回归全部重跑 | **高** |
| 定制误伤 | 改 QQ 通知逻辑 | 三个包同时受影响，但只有 Maadori 会测 | 中 |
| git 状态污染 | MaaEOV 跑 `git checkout tag` | Maadori 定制分支被切走，下次编译丢了定制 | 中 |
| GPL 溯源断裂 | 三产品用同一份产物但源码状态不可重现 | 无法给出"这个包对应哪个 commit"，GPLv3 义务履行有瑕疵 | 中 |
| 用户环境串味 | 两产品装在同一个目录 | 配置/instances 互相覆盖 | 低（各有独立包） |

## 七、决策矩阵：什么时候该升级隔离强度

| 信号 | 动作 |
|---|---|
| 出现第 2 个需要 GUI 层定制的产品 | 直接上方案 3，不要临时改共用源码 |
| 两个产品的 MaaFramework 版本必须不同 | 方案 3 的 A2（按 Brand 锁版本）立刻做 |
| 某产品的 C# 改动量超过总量的 30% | 考虑把该产品拆到独立 fork（方案 4） |
| 上游发布破坏性变更（v3 接口 / pipeline v6） | 方案 3 的价值最大化：一份代码适配，三处受益 |
| 只有一个产品在活跃迭代，其余只是分发现状 | 暂缓改造，但要先把 A1（产物目录）和 A5（更新源）拆掉 |

---

## 八、一句话总结

**共享框架、隔离品牌、按产品锁版本。** 源码一份，产物三份，边界由编译参数强制 —— 这样上游同步做一次，品牌不会串味，框架升级不必全体陪跑。
