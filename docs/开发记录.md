## 记录规则

1. **条目内容**：日期、变更摘要、涉及文件（仓库内相对路径）、实现要点、验证方式、提交状态。
2. **排列顺序**：按时间先后**正序**，新记录追加到文件末尾。
3. **提交状态**：已提交附 commit 短 SHA；仍在工作区的标注 `WIP（未提交）`。
4. **根因优先**：修复类记录必须写明根因，避免同类问题复现。
5. **构建与部署**：涉及编译产物的改动，需写明构建命令、产物路径与部署方式。

## 通用构建 / 部署要点（长期有效）

- **构建**：`dotnet build MFAAvalonia.Desktop/MFAAvalonia.Desktop.csproj -c Release`
  （增量约 30s，产物在仓库根 `bin/AnyCPU/Release/`）。
- **真程序集是 `MFAAvalonia.Core.dll`（约 3.3MB）**；`MFAAvalonia.dll`（约 179KB）只是启动器壳。
  验证改动是否编译进去，**必须搜 `MFAAvalonia.Core.dll`**，验证手法为二进制搜 UTF-16LE 字符串。
- **本地化资源**在 `MFAAvalonia.Core.resources.dll`（satellite，按 `en-US/`、`ja-JP/`、`zh-Hant/`
  子目录）；**简体是中性资源、编进主 dll**，没有 `zh-Hans` 目录。
- **部署（本地运行副本）**：MFA 若使用项目根的分发副本，改完需单独同步
  `MFAAvalonia.Core.dll` + 3 个 satellite resources。
  ⚠️ **同步前必须先关闭 MFA**——运行中的 MFA 会锁住 `MFAAvalonia.Core.dll` 导致 `PermissionError`。
- ⚠️ **`dotnet build` 的常驻构建服务也会锁住输出 dll**：若同步时报 `Permission denied` 而
  `tasklist` 里看不到 MFA 进程，真凶是 MSBuild / VB-C# 编译器服务器（build server）。
  **先 `dotnet build-server shutdown` 再复制。**
- **Avalonia XAML 编译进 Core.dll，改动后必须重启 MFA 才生效。**

### 2026-09-26 · 任务结束/错误附带截图与运行日志

- **变更摘要**：QQ 渠道在**任务结束/错误**时可附带一张当时画面截图 + 最近若干条运行日志，
  各由一个开关控制（**默认开启**）。
- **涉及文件**：
  | 文件 | 改动 |
  | --- | --- |
  | `Configuration/ConfigurationKeys.cs` | 新增 `ExternalNotificationQQBotSendImage` / `…SendLog` |
  | `ViewModels/.../ExternalNotificationSettingsUserControlModel.cs` | 两个 `[ObservableProperty]` 布尔属性（默认 `true`） |
  | `Views/.../ExternalNotificationSettingsUserControl.axaml` | QQBot 卡片新增两个复选框 |
  | `Helper/ExternalNotificationHelper.cs` | `ExternalNotificationAsync` 新增 `imageBytes` / `imageFileName` / `logText` 参数；新增 `QQBot.SendImageAsync` 与 `UploadImageAsync` |
  | `Extensions/MaaFW/MaaProcessor.cs` | 新增 `CaptureNotificationImage()` 与 `BuildRecentLogText()`，并在结束/错误两个调用点传入 |
  | `Helper/LangKeys.cs` + 4 份 resx | 各 +2 键 × 4 语言 |
- **截图实现要点**：
  - 取图：`MaaProcessor.GetImage(controller, ShouldScreencapForLiveView())` 返回 **`MaaImageBuffer`**，
    用 **`TryGetEncodedData(out byte[])`** 得到**标准 PNG** 字节。
  - ⚠️ **不能用 Avalonia 的 `Bitmap.Save(Stream)`**——其输出格式不被 QQ 接受（实测 850019）。
  - ⚠️ **不能用 `GetLiveViewCached()`**——它内部 `GetScreenshotController(false)` 不触发连接、
    `GetImage(..., false)` 只读缓存，任务结束/停止后主 tasker 的 controller 已失效 → 取不到画面。
    **必须用 `GetLiveView()`**（触发重连），并在为 null 时 `Thread.Sleep(500)` 重试一次。
  - ⚠️ `MaaImageBuffer.TryGetEncodedData` 有 `out byte[]` 与 `out Stream` **两个重载**，
    写 `out var x` 会报 **CS0121 二义性**，必须显式 `out byte[]`。
- **日志实现要点**：取 `MaaProcessor.LogItemViewModels`（`LogItemViewModel.Content`）最近
  `maxLines = 25` 条、`maxChars = 900` 字符，接在文字通知之后。
- **QQ 富媒体分片上传（四步，无 base64 直传）**：
  1. `POST /v2/users/{openid}/upload_prepare`
     （必填 `file_type / file_size / file_name / md5 / sha1 / md5_10m`，
     `md5_10m` = 前 10002432 字节的 MD5）→ 返回 `upload_id` / `block_size` / `parts[].presigned_url`
  2. 逐片 `PUT` 到 `presigned_url`（分片二进制）
  3. `POST .../upload_part_finish`（`upload_id` / `part_index` / `block_size` / `md5`）
  4. `POST .../files`（带 `upload_id` 合并）→ `file_info`
  5. `POST .../messages`，`{ msg_type: 7, media: { file_info } }`
  - 截图 < 5MB（默认 `block_size`）→ **通常只有 1 个分片**。图片软限 20MB / 硬限 200MB。
- **★ 根因（图片始终发不出，QQ 返回 850019「富媒体文件格式不支持」）**：
  `upload_prepare` 返回的 **`parts[].index` 从 1 开始**（官方文档写的是"从 0 开始"，**实测为 1**）。
  按 `offset = index × block_size` 计算偏移，会使 **首片就越过整个文件** → `length = 0`
  → **PUT 实际上传了 0 字节**（而 **HTTP 状态码仍是 200**，只看状态码无法察觉）
  → 合并时判定文件非法 → 850019。
  **修复：偏移必须按分片顺序累积**，`index` 仅用于 `part_finish` 的 `part_index`：
  ```csharp
  var offset = 0L;
  foreach (var part in parts)
  {
      var length = (int)Math.Min(blockSize, Math.Max(data.Length - offset, 0));
      var chunk = new byte[length];
      Array.Copy(data, offset, chunk, 0, length);
      offset += length;
      // …PUT chunk…
  }
  ```
- **排查手法（高价值，可复用）**：**用 Python 独立复现 MFA 的 HTTP 链路**
  （从 `data/config.yml` 读凭据），一次即定位问题，省掉 C# 改 → 编译 → 部署 → 重启的整轮往返。
  复现时打印出 `PUT part 1: 200 (bytes=0)` 才暴露问题。
- **提交**：`41359cd`

### 2026-09-26 · 已知问题：任务结束后截图必然失败（用户实测）

- **现象**：QQ 通知「附带截图」已勾选、渠道已绑定，任务结束后只收到文字（含日志），**没有图片**。
- **根因（用户 `maafw.log` 实锤）**：任务结束后 MaaFramework 内核**立即把 controller 置为 `inactive`**：
  ```
  11:56:26.167  Controller.Action.Succeeded  {action: "screencap"}   ← 任务期间最后一次成功截图
  11:59:25.238  Tasker.Task.Succeeded                                ← 任务结束
  11:59:25.239  Controller.Action.Starting   {action: "inactive"}    ← controller 立刻 inactive
  （此后到日志结束，再无任何 screencap 动作）
  ```
  而 `CaptureNotificationImage()` 在任务结束后才取图，此时 controller 已断开；
  `GetScreenshotController(true)` 内的 `TryConnectForLiveViewAsync()` 是**异步 fire-and-forget**，
  现有实现只有 **2 次尝试、间隔固定 500ms** —— 远不足以完成一次重连 → 取不到画面 → 返回 null
  → **静默不发图**（不报错、不打日志）。
- **关键判据**：`maafw.log` 中 `ScreencapFailed` 计数为 **0** —— 说明**根本没发起截图动作**，
  而不是"截了但上传失败"。据此可排除图片格式（850019）与上传链路。
- **为何自测通过**：本机任务结束后 MFA 仍保持连接，2×500ms 内能拿回画面；
  用户环境 controller 被明确置为 inactive，重连耗时更长 → **稳定失败**。
  同一份代码两种表现，属环境时序差异。
- **涉及文件**：`Extensions/MaaFW/MaaProcessor.cs`（`CaptureNotificationImage`、`ShouldScreencapForLiveView`）
- **修复方向**（尚未实施）：
  1. **任务运行期间缓存最后一张成功画面**（每次 screencap 回调时留存 PNG 字节），
     通知时直接取缓存 —— 与 controller 是否 inactive 完全解耦（**首选**）。
  2. `CaptureNotificationImage` 改**退避重试**（500/1000/1500/2000ms）+ 轮询 `controller.IsConnected`，
     替代固定 `Thread.Sleep(500)` 直取。
  3. **消除静默失败**：三个前置条件（未勾选 / 未验证 / 渠道未启用）与取图失败均需打日志。
  4. 兜底：取图失败时在文字末尾附「截图获取失败」提示，让用户可感知（当前退化为静默只发文字）。
- **提交**：`41359cd`

### 2026-09-26 · 修复：任务结束后截图必然失败（方案 1 缓存画面 + 方案 3 补诊断日志）

- **变更摘要**：彻底修复「任务结束后附带的截图取不到、通知静默无图」。
  取图策略改为**优先用任务运行期缓存的画面**，并把原先静默失败的三处前置条件与取图失败全部补上日志。
- **涉及文件**：`Extensions/MaaFW/MaaProcessor.cs`
- **实现要点**：
  1. **运行期缓存（方案 1，根治时序）**：新增字段 `_lastNotificationImage` / `_lastNotificationImageAt`，
     并在 **`GetImage()` 的成功返回路径**上调用新增的 `UpdateNotificationImageCache(buffer)`。
     选 `GetImage` 作为切入点是因为它是**所有截图（含任务运行期 MAA 内核的截图）的公共出口**，
     覆盖面最全、改动最小。缓存的是 `TryGetEncodedData(out byte[])` 出的标准 PNG 字节，
     与通知上传所需格式完全一致，**与 controller 是否 inactive 彻底解耦**。
  2. **取图顺序改为「缓存优先 → 退避重试实时取图」**：
     先取 `_lastNotificationImage`；为空时才实时截图，且把原先的「2 次 × 固定 500ms」
     改为 **退避重试（300/800/1500/2000ms）+ `WaitForControllerReconnect()` 轮询 `IsConnected`**，
     不再固定 sleep 后直取。新增 `WaitForControllerReconnect(int totalMs)`（100ms 步进轮询）。
  3. **补全诊断日志（方案 3）**：三个前置条件原先一律静默 `return null`，现分别记录
     「未开启「附带截图」」/「QQ 机器人尚未完成绑定验证」/「QQ 机器人渠道未启用」，
     让用户侧可自查；成功时记录数据来源（`使用运行期缓存：N 字节（截于 HH:mm:ss）`
     或 `已生成：N 字节（第 N 次尝试）`）；彻底失败时给出明确原因。
  4. **★ 深拷贝 + 节流（验证前加固，重要）**：
     - **必须深拷贝**：官方 XML 文档对 `TryGetEncodedData` 的 `Stream` / `ReadOnlySpan` 重载
       明确写着 **「Avoids disposing IMaaImageBuffer before the stream/span is read」**，
       说明取到的是**内部缓冲区视图**；而 `GetImage` 的调用方拿到返回值后会立刻 `using` 释放。
       若直接持有 `out byte[]` 的引用，缓存到的可能是失效/被复用的数据。
       故一律 `new byte[len]` + `Array.Copy` 拷贝后再缓存（既有 `FocusHandler.StoreImageAndGetUrl`
       与 `MFAExtensions.ToBitmap` 也都采取"立即拷贝"的用法，印证了这一点）。
     - **必须节流**：任务运行期每秒可能截图数次，每张都拷贝 1MB+ 会产生无谓的内存分配与 GC 压力；
       通知只需"当时的一张代表性画面"，故加 `NotificationImageCacheIntervalMs = 1500` 节流
       （**首次无条件缓存**，否则"截图测试"这类毫秒级短任务会一张都留不下来）。
     - 缓存首次就绪时打 Info 日志 `通知画面缓存已就绪：N 字节`，便于确认缓存真的被填充。
- **构建 / 部署**：
  - `dotnet build MFAAvalonia.Desktop/MFAAvalonia.Desktop.csproj -c Release` → **0 错误**。
  - 验证：`MFAAvalonia.Core.dll` 二进制含全部新增中文字符串常量。
  - 部署：同步 `MFAAvalonia.Core.dll` + 3 个 satellite resources 到运行副本（项目根）与
    `Maadori/` 暂存目录，三处 md5 一致（`7075df804c319c1e8339ed607451c784`）。
  - ⚠️ 同步前确认 MFA **未运行**（运行中会锁 Core.dll）。
  - 加固后重新编译部署，三处 md5 一致 **`5e56ace25ed56aeff5d90e016e9b89eb`**。
- **验证过程中的发现**：
  - **本机 MuMu 在 `D:/MuMu/`**（非 `D:/Netease/MuMu`；后者是测试用户环境），配置见
    `config/instances/*.json` 的 `AdbDevice.AdbPath`。
  - **MFA 启动后不会自动跑任务**：日志会走到「控制器检测」并打印设备/ADB/截图模式后**停住**，
    必须手动点「开始任务」才会真正执行（实测日志冻结 105 秒无新内容）。
    因此**无法全自动验证**，需人工点一次任务。
  - MFA 只支持 `--identify` 命令行参数，**没有启动任务的 CLI**。
- **待验证（已本地通过）**：见上一条「关键修正」，本地已跑通完整链路
  （运行期缓存 → 通知取缓存 → 图片发送成功）。**发版后需测试用户确认**。

### 2026-09-26/27 · ★ 关键修正：任务运行期的画面并不会自动进缓存

- **首次验证暴露的设计错误（00:13）**：原以为 `GetImage()` 是"所有截图的公共出口"，
  只要在它的成功路径上挂缓存就能自动留下一张任务运行期的画面。**实测证明该假设错误**：
  ```
  00:13:16.252  通知画面缓存已就绪：1559805 字节
  00:13:16.253  通知截图已生成：1559805 字节（第 1 次尝试）   ← 走的是实时截图，不是缓存
  ```
  缓存与取图**仅差 1ms** —— 说明缓存是在"通知取图那一刻"才首次填充的，
  **任务运行期一次都没填充过**。两个原因：
  1. **MAA 内核（tasker）为流水线识别所做的截图发生在 C++ 层，不经过 C# 的 `GetImage()`**；
  2. 实时画面定时器虽有周期截图，但被 `IsLiveViewExpanded && EnableLiveView`
     两个 **UI 条件**挡着（`TaskQueueViewModel.cs:3290`），用户不展开实时画面面板就一次都不截。
- **修正**：新增**不依赖 UI 的运行期缓存循环** ——
  `StartNotificationImageCacheLoop()` / `StopNotificationImageCacheLoop()`，
  挂在 `RunTaskChainAsync` 的 `try/finally` 上（必须挂这里：`EndTaskRun()` 在 finally 中，
  保证任务结束/取消/异常都能停掉循环）。
  循环内仅在 `MaaTasker?.IsRunning == true` 时取图，用 `GetScreenshotController(false)`
  （`test=false`，避免触发额外重连干扰主流程）+ `GetImage(controller, true)`。
  周期 `NotificationImageCacheLoopIntervalMs = 3000`；走**独立截图 tasker**，不干扰主任务；
  EmulatorExtras 单次仅 8~11ms，开销可忽略。
- **最终验证通过（00:19）**：
  ```
  00:19:11.586  [op=StartTask]  通知画面缓存已就绪：949483 字节          ← 运行期就填充
  00:19:26.081  [op=StopTask]   通知截图使用运行期缓存：937247 字节（截于 00:19:23）  ← 关键
  00:19:27.023  [op=StopTask]   QQ机器人消息发送成功
  00:19:31.207  [op=StopTask]   QQ机器人图片发送成功
  ```
  缓存画面截于 00:19:23、通知取用于 00:19:26，**仅差 3 秒** —— 确实是任务结束时的画面。
  至此即使 controller 在任务结束时立刻 `inactive`，图也能照样发出。
